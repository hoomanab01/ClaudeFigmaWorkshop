03

Read this first

≈ 5 min

There is a claim going around that you can paste a design into a model and get a working product out. It is half true, and the half it misses is the half you own.

A model reproduces the structure it is handed. Give it a screenshot and it has to guess. It invents names for things that had none, hardcodes every colour it can see, builds one static view because it was shown one static view, and rewrites half the file the moment you ask for a change. Give it a system and the guessing stops. Named components become named code. Tokens become variables. The states you drew get built, because they exist.

Same model. Same prompt. Different file.

Your design system is the prompt.

That is the argument the whole evening rests on, and it means most of the quality is decided before anyone types anything. Three consequences, and they are all yours.

Naming became functional

A layer called Frame 427 used to be untidy. Now it is an instruction with nothing in it. A layer called Badge/Status/Open produces a component your team can reference, extend and find again. Renaming a file is not admin any more. It is writing the spec.

The system is the leverage, not the screen

Anyone can generate one screen. The real test is the second one, and the fiftieth, and what happens when a client asks for a different accent colour at four on a Thursday. If that change costs you one token, you built a system. If it costs you an afternoon, you built a very tidy screenshot.

Your eye is the part that did not get automated

The model is extremely good at producing something that looks finished. It is not good at holding a spacing scale, keeping hierarchy intact once real content arrives, building the states nobody drew, or leaving a focus ring where a keyboard user needs one. Those are design judgements and they are still yours. On the night we turn them into a six-pass critique you can run on anything, including work that has nothing to do with this.

You do not have to agree with any of this in advance. You will get to test it directly: at one point in the evening you will change a single token and watch the whole screen follow, or find that it does not, which is the more useful outcome.

04

Claude Code or a Figma prototype

≈ 4 min

The honest answer, before anyone sells you anything. These are not competing tools. They answer different questions, and most of the waste comes from using one to do the other's job.

Reach for a Figma prototype
  • You are testing a sequence, and only the order of screens matters
  • You need it inside the hour and it only has to survive one meeting
  • The audience needs to see intent, not behaviour
  • The idea lives in motion and transition, where Figma's tooling is simply better
  • You are still deciding what to build
Reach for Claude Code
  • It needs real content, real lengths, real state. A prototype fakes all three
  • Someone has to use it on their own device, at their own size, with a keyboard
  • You will change it repeatedly and want the change to propagate
  • It is going to become the real thing, or be handed over as more than a picture
  • You have already decided, and now you need proof

The short version

Prototype to decide. Build to prove. A prototype answers "is this the right flow"; a build answers "does this actually hold up when the content is long, the network is slow and the list is empty". Neither answer substitutes for the other.

Why a tool you type into, rather than one you click in

Plenty of tools now generate an interface from a canvas, and they get to a first screen faster. What you get here instead is the file: something with a history you can read, that you can point at a design system and hold to it, and where changing one value changes fifty places. That matters from roughly the second screen onwards, which is also where most real work starts.

What this is not

What you build on the night is not a production codebase, and we will not pretend otherwise. It is a real, running interface built from your design decisions. Where that is enough and where it is not is a fair question, and a good one for the last half hour.

05

The starter file

≈ 3 min

Everybody builds from the same file, so nobody spends the evening deciding what to make. It is a support inbox called Signal: unglamorous on purpose, and rich in exactly the things that expose a weak handoff.

Duplicate it to your own drafts before you arrive, and spend three minutes reading the layer names. That is the only homework in this section, and it matters more than it sounds.

Tokens
Colour, spacing, radius, type and density, as Figma variables rather than styles
Components
Nine, with every variant drawn: buttons, status badges, filter chips, ticket rows, metric cards, empty and loading states
Frames
Desktop and mobile, plus separate frames for empty, loading and error
One more
A frame called Change Request. Do not open it before the night, it gives away the best part

If you have only ever used styles

This is the one Figma feature worth ten minutes before you arrive. A style is a saved appearance you apply to a layer. A variable is a named value that layers point at, which is what lets one change travel through a whole screen instead of stopping at the layer you edited. The starter file is built on variables throughout. You do not need to be able to build them yet, only to recognise them when you open the file.

08

Words we will use

≈ 2 min

So that nobody spends the evening quietly decoding a term rather than asking about it.

Token
A named value, like a colour or a spacing step, that things point at instead of holding a raw number
Variable
Figma's implementation of a token. Distinct from a style, which saves an appearance rather than a value
Reference
When one thing points at another rather than copying it. A row that references a badge component updates when the badge does. A row with its own hand-built pill does not
State
What a thing looks like under different conditions: hovered, focused, disabled, empty, loading, failed. Most designs draw one state and inherit the rest by accident
Context file
A plain text file in a project that the model reads every time, so you stop repeating the same instructions in every conversation
The connection
The mechanism that lets Claude Code read your Figma file directly. You do not need to know how it works, only that it is on
Terminal
The text window you type commands into. Claude Code runs there rather than in a browser tab
09

If something breaks

I cannot install anything on my work laptop

Ask IT this week, and if the answer is no, bring a personal machine. Tell us in advance either way and we will pair you with someone rather than leave you watching.

I am not a developer. Is this going to lose me?

No. You will type into a terminal and you will read code you did not write, but nothing here asks you to write code. Every design judgement in the room is one you already make. The technical floor is the setup above, and once it is done it stays done.

Can I bring my own project instead of the starter file?

Not for the build block. Everyone on the same file is what makes the critique hour work, because we can compare builds directly. Bring your own file for the questions at the end and we will look at it properly.

Do I need to finish the reading?

The setup is the part that matters. The reading saves you about fifteen minutes of orientation in the room, but you will not be lost without it.

What if I cannot make it any more?

Release your ticket on the event page as early as you can. There is a waitlist and these rooms are small.
